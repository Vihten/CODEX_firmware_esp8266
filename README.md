# CODEX firmware ESP8266

OTA artifacts generated by LED Forge.

Release `1791885372945` uses D4 / GPIO2 asynchronous UART1 output at a
30 FPS target. The signal wire must be on D4, not D2 / GPIO4. The manifest
declares `ledDataPin: 2` and `ledTransport: async-uart1`. New asynchronous
firmware rejects OTA images that do not match this transport.

HTTP replies now include Content-Length so browsers do not depend on a
delayed TCP FIN to finish reading. ESP8266 polls outstanding acknowledgements
between animation frames for at most 250 ms before graceful close. There is
no blocking ACK wait across frames. Wi-Fi modem sleep is disabled on station
startup for this continuously powered display. Health reports RSSI, sleep mode,
maximum portal service gap, ACK deadlines, close failures and write retries.
Low-memory diagnostic responses return 503 instead of a partial health body.
ESP8266 filesystem auto-format on mount failure is disabled to protect saved
settings. A fresh/unformatted device requires explicit filesystem provisioning;
mount failure enters recovery rather than silently formatting storage.

The preceding D4 build completed a 60-minute PSU-powered observation with no
resets, Wi-Fi disconnects or LED transmission stalls, and all 36 page requests
successful. Ten health requests timed out. TCP phase probes also found delayed
connection establishment; those delays are not claimed to be fixed solely by
HTTP framing. This release has build/native regression checks, but requires a
new hardware observation after installation. The brief startup white flash on
D4 remains unresolved. Saved Wi-Fi, account binding and preferences are not
erased by application OTA; no account password or OAuth token is in the image.

Release `1791809772841` restores the requested 30 FPS target on GPIO4,
removing the temporary 40 ms network gap. Overruns still yield for 1 ms
and rebase scheduling; elapsed-time effect progression is retained.
Physical frame rate and long-run stability require device testing.
The 1000-LED bit-banged output still masks interrupts for about 30 ms.

Network recovery uses checked STA-only startup, AP-only fallback, bounded
station attempts and retries, and active/queued HTTP cleanup before AP mode.
HTTP backlog is now two; validated HTTP/1.1 Expect requests receive bounded
100 Continue replies, and fully queued responses close gracefully.
Exhausted low-memory recovery may perform a controlled restart after radio
shutdown and 60 seconds below the recovery threshold; healthy operation
does not periodically restart. Earlier recovery details below are historical.
Direct telemetry and color tables support 12 agents; eight fit within this
capacity. This is not a certification of eight-agent throughput.

Release `1791790784813` fixes a network-recovery lockout between 8 and 16 KB
of free heap. ESP8266 station servicing now runs outside animation gating.
Abandoned/error HTTP connections abort without flushing; successful responses
retain graceful connection-close framing. If buffer cleanup leaves memory low,
recovery turns the radio off once, waits at least 500 ms, and restores STA only
when memory is sufficient. This does not reboot the MCU. `/health` includes
Wi-Fi state and recovery heap/radio counters for further diagnosis.

The firmware addresses ESP8266 reconnect churn and network-buffer
retention after a captured SDK scan crash with only 656 bytes of free heap.
Wi-Fi fallback now measures continuous disconnection, waits at least 60 seconds,
and does not switch modes during an active connection attempt. Attempts stop
after 15 seconds with 30-second backoff. SDK automatic reconnect is disabled.
Portal backlog is limited to one; low-memory recovery stops admission, aborts
active/pending portal contexts without flushing, frees UDP/DNS resources and
pauses station retries without rebooting the MCU or erasing saved credentials.
LED frame transmission pauses during recovery/scanning. ESP32 policy is unchanged.
Long-run stability still requires device observation; the precise source of all
memory retained before the captured crash is not claimed as proven.

The firmware includes allocation-free ESP8266 RTC crash diagnostics
exposed through `/health`: sampled heap/block minima, last allocation failure,
execution stage, previous-crash version/uptime/registers and bounded candidate
return addresses. The 272-byte RTC record preserves the OTA command region;
there are no periodic flash writes. Samples are not exact fault-time memory
measurements, and candidate addresses are not an unwound call stack. This
release also stops the UDP receive budget from discarding the fifth packet.

Stages: 1 startup, 2 portal, 3 telemetry, 4 OTA, 5 frame rendering,
6 LED output, 7 schedule time, 8 discovery, 9 persistence, 10 memory recovery.

The animation launches meteors in globally spaced pairs, with
0.6-second pauses at 30 FPS. One active user retains full 1/2/3/5/7 bursts.
With multiple active users, bursts and concurrent owner flights are capped
at three, with eight concurrent flights overall. Idle connected users do
not reduce the solo allowance. Round-robin admission keeps colors fair;
already launched flights finish when the policy tightens.

The gradient halves the white tint in meteor colors: the head
uses 25 percent white rather than 50 percent, retaining full peak brightness
and more saturated agent colors throughout the body. Motion is unchanged.

The animation includes a very faint lingering meteor wake, fading
quadratically over up to 0.6 seconds with a small late vertical dispersion.
Sparse samples stay at their historical flight positions; bright objects are
protected. No additional pixel history buffer is allocated. Additive writes
preserve background channels at low matrix brightness. The previous gentle
shimmer, head, gradient, dotted rear, and blinking tip are unchanged.
Global brightness, network settings, and portal memory fixes are preserved.

The firmware releases portal buffers and client contexts after responses,
timeouts, malformed requests, and Wi-Fi loss. Low-memory HTML requests receive
503 instead of attempting large allocations. ESP8266 OTA defers its TLS probe
when free heap or the largest block is insufficient. `/health` includes web
cleanup counters and exception addresses; the previous reset cause remains
under investigation rather than being assumed to be a heap leak.

The animation uses a single bright, color-tinted head with a contiguous
central body. Only the rear tail is dashed. The quadratic 72-to-6 percent
brightness gradient is preserved. Hot highlights
transition into the saturated agent color along the whole tail. The last dash
pulses every 36 frames, blending into the background as it fades; the immediately
preceding pixel remains transparent. Detached tail particles continue to fade.
All five load levels and per-agent colors
remain supported. Particle work is bounded and does not allocate heap memory.

This release also fixes writable-capacity reporting for the bounded manifest
writer. Controllers on `1791531077393` cannot fetch an OTA manifest correctly
and require one USB application-flash update, without erasing saved settings.

The firmware also unifies the daylight sky palette, shows the station IP
for at least five seconds, and keeps recovery networking available when artwork
cannot be loaded. Portal responses and the OTA manifest have bounded memory use;
overdue LED frames yield to the Wi-Fi stack. `/health` exposes uptime, reset
reason, and heap statistics for diagnosing hardware stability without USB.

- `firmware.bin` — uncompressed ESP8266 application image for USB recovery.
- `firmware.bin.gz` — compressed image used for Wi-Fi OTA.
- `manifest.json` — OTA version, download URL, and compressed-image checksums.

The controller checks this manifest over Wi-Fi after startup and periodically while
online. The firmware image includes the matrix artwork, so a normal OTA update
does not require LED Forge, USB, or a PC. The MD5 value is verified by the
ESP8266 updater before the new image is activated; SHA-256 is provided for
independent release verification. USB remains available for recovery.

The controller downloads the compressed image from the GitHub API in verified
byte ranges, resuming an interrupted transfer before activating the image.
The current ESP8266 client does not validate GitHub's TLS certificate; manifest
checksums detect corruption but do not authenticate an update against a
network attacker. Keep repository publishing access restricted.

ChatGPT/Codex passwords and OAuth tokens are never included. Authentication remains in the local Codex app-server on the paired PC.
